# Account-bound persistence and recovery design

Status: proposed architecture; implementation and security review required before enabling automatic backup/restore. Scope: `vagabond1215/TORN`, `/docs/` only.

## Goals and non-goals
- Preserve guide-created data across site storage clears, reloads, API key rotation and migration to another browser or device.
- Use the canonical numeric player ID returned from a successful Torn own-account API request (existing `user/basic` connection path), not a typed ID, name, API-key hash, or imported filename, as the account namespace. A public player ID is not authentication. A valid key identifies the account to the guide but is not independent proof of human ownership; stolen keys remain a risk.
- Never export, persist in companion backup, transmit to backup services, or log an API key, session cookie, or authentication record. Preserve the existing separately consented Remember API Key behavior; prefer memory-only authentication. Never store real user backups in the public GitHub repository.
- Static Pages has no trusted backend or private per-user database. No automatic cross-device lookup from player ID alone. No unrequested filesystem scanning, new network destination, or credential exposure.

## Three storage layers
1. Fast working store: existing account-scoped localStorage and IndexedDB; migrate durable records through an explicit schema registry, rather than blindly copying all keys. Refreshable API snapshots are optional cache, not authoritative backup state; any restored snapshots retain original fetch ages and must be refreshed before recommendations.
2. Optional companion vault: after explicit enrollment, keep bounded, versioned per-player snapshots in userscript GM storage, independent of guide-origin site storage. A cleared guide can reconnect with its API key and automatically request the matching enrolled account snapshot if authorized; do not automatically disclose an unencrypted backup in response to a page-provided ID or DOM event. The current event bridge is not a trusted authentication boundary. Design a companion-mediated approval/recovery flow or encrypted vault unlocked with an independent user-held secret; require user approval for first enrollment and untrusted recovery. Never send the API key to the companion. Retain a last-known-good and previous generation; acknowledge durable writes; report failures/quota instead of claiming success.
3. Portable versioned file export/import: store outside browser site data, optionally in user's own synced directory. Standard file chooser fallback for all supported browsers; optional File System Access directory selection on supported browsers, with user-granted permission and re-selection if cleared. No silent disk discovery. Match verified account ID from validated content, never filename alone; automatically select/merge a unique eligible backup within the explicitly authorized directory. Encrypt sensitive portable backups by default with authenticated encryption (Web Crypto AES-GCM, random salt and IV, password-derived key with versioned KDF parameters); independent recovery passphrase, not API key or public ID. No backend required for local/cloud-folder recovery. A future private hosted sync service would require actual authentication and access control; not implied by Pages or this plan.

## Schema, integrity, merge
- Versioned envelope: schema version, playerId, backupId, createdAt, updatedAt, per-section revisions, data sections, format metadata and integrity check; encryption protects authenticity when the secret is held by the user. Treat imported data as untrusted, validate shape, size, numeric bounds, allowed keys and schema before applying. Reject mismatched owner, unknown future schemas, corrupt files and oversized records. Do not execute imported data.
- Include preferences/build, templates, budget settings, manual calendar events, active session and completed prefix, training/activity ledgers, restock rules, crime observations, personal log archive and optionally large market archive as separately chunked data. Distinguish device-global display preferences from per-player records. Explicitly inventory each existing key/store and version. Avoid double-copying companion archives. Do not restore key/auth records or transient request state.
- On startup, stage recovery before defaults or empty caches can overwrite a backup. Recheck current account and connection epoch before committing. Prefer newest valid per-section revision; immutable financial/log events merge by stable ID with conflict checks and deletion tombstones. Never use timestamps alone to overwrite active session or ledger; retain conflicts and require review where divergent confirmed actions cannot be safely merged. Restore atomically where possible, otherwise journal/recover partial writes. Preserve an undo snapshot. Multi-tab synchronization must prevent competing writes and restore loops.
- Auto-save durable changes with debounced, acknowledged writes and bounded retained revisions; checkpoint before page unload only as best effort, not sole persistence. Distinct status: saved locally, companion mirrored, portable backup last written, permission needed, backup failed. Explicit disable/forget/purge controls separate logout and API key replacement from deletion of account history.

## Sequence and acceptance
Insert a persistence foundation before Phase 1B.3 ledger schema is finalized. First audit storage keys and account scopes; implement typed account-state adapters, portable file export/import, strict schema and merge rules; then companion enrollment and authorized automatic restore; then optional directory mirroring and archive migration. Ledger and session recovery build on stable event IDs, revisions and tombstones. Never require companion or cloud account for ordinary use. 
Acceptance: site-data clear with companion intact; full browser reset with external file; key rotation same player; different player and spoofed ID refusal; failed API identity verification; same-player multiple backup generations; stale API cache not promoted; partial import failure; malformed/tampered/encrypted backup; concurrent tabs; quota error; deletion not resurrected; unsupported file API; disconnected/missing extension; no key/cookie in any export/bridge. Validate actual browser behavior as well as synthetic fixtures. No gameplay actions automated.
